# Models, the in-use model, and settings changes during a turn

## What the Claude adapter does with models (read-only study)

Studied: `@agentclientprotocol/claude-agent-acp` 0.97.0 under the fnm node install (`dist/acp-agent.js`, `dist/session-model.js`, `dist/resumed-session.js`). Nothing in it is patched. It needs the `type` field (`"id"` for a choice from a list, `"boolean"` for a switch) in `session/set_config_option`; Studio sends it itself (`breadth.build_config_request`). Without it the adapter ignores the change.

- **Where the list comes from.** `session/new` and `session/load` share one code path (`createSession`). The Claude CLI's `initializationResult.models` is the base list (`acp-agent.js:9112-9127`). It is then narrowed by the user's `availableModels` allowlist in Claude settings (`settings.json` in the user, project or local scope, `applyAvailableModelsAllowlist`, `session-model.js:287`) and by managed `deniedModels`. A gateway set through `providers/set` narrows it further (`narrowToGatewayModels`, `session-model.js:361`). The `model` option is built from what is left (`buildModelConfigOption`, `session-model.js:164`). A client that sends the AIR "recommendedValue" capability also loses the `default` row. Studio does not send it. Nothing about the list depends on loading versus creating a session, so one choice means the CLI, the settings or the account only offered one.
- **Which one is current.** `getAvailableModels` (`session-model.js:390`): `ANTHROPIC_MODEL` in the adapter's own process environment wins, then `settings.model`, and only then, for a resumed session, the model of the last real assistant record of the transcript (`resumed-session.js`, used at `acp-agent.js:8668-8674`). A model named by the environment or settings is pushed back to the CLI with `setModel` (`session-model.js:473`), so a stale alias can be advertised as current while the CLI answers with something else. This is why the transcript is the better evidence of what is in use.
- **What a client can send.** `session/set_config_option` for `model` accepts only a value that is in the advertised options, the current value, or a fuzzy alias that resolves to one of the advertised options (`acp-agent.js:6860-6900`). A model that is not in the list is refused with "Invalid value", so Studio does not offer to send one. `_meta.claudeCode.options` on `session/new` or `session/load` is spread into the SDK options (`acp-agent.js:8868`), including `model`, `settings` and `env`, but the allowlist comes from the settings files, not from `_meta`, and `ANTHROPIC_MODEL` is read from the adapter process, not from `_meta.env`. Studio does not set these.
- **The `/model` command.** A `/model <name>` typed as a prompt is run by Claude Code as a local command. The adapter's `PostModelSwitch` hook then re-syncs its model option and tells the client (`acp-agent.js:8968-8990`). This is the legitimate way to a model outside the list. Studio shows a "Start a /model message" button in the Model chip when the agent lists a `model` command, and shows the model the agent then reports. Whether the command is offered depends on the Claude Code version (the code comment names CLI 2.1.251+) and is not tested here: real adapters are never launched by the test suite.
- **A live signal.** Usage updates carry `_meta["_claude/model"]` with the model of the latest reply (`acp-agent.js:2957-2967`). Studio keeps it (`breadth.responseModel`) and uses it when no transcript is found.

When the advertised list has one choice the chip says "This agent offers no other models for this conversation." and, when `/model` is available, how to ask for another.

## The model in use

`monitor.latest_assistant_model` reads the newest real assistant record of the conversation's own transcript (a bounded tail read, 256 KiB widening to at most 4 MiB, cached by size and mtime, never writing). Claude: `message.model` of `type: "assistant"` records; `<synthetic>` and sidechain records are skipped. OMP: `message.model` (with `message.provider`) of `role: "assistant"` records in `~/.omp/agent/sessions/<project>/<timestamp>_<id>.jsonl`; OMP's `model_change` records name the configured `provider/model`. The web server adds it to `/api/live/state` as `inUse: {model, provider?, source: "transcript" | "agent-usage"}` (or `null`). A newest record larger than 4 MiB gives "unknown", never an older model.

The Model chip shows the in-use model with a friendly name (`claude-opus-5-5` becomes "Opus 5.5"; ids that are not Claude's are shown as they are). If the agent advertises a different model it adds a warning marker: "The agent reports Sonnet 5.5, but its replies are coming from Opus 5.5." The comparison warns only with evidence: two recognisable models that differ, or two plain names that differ. "Default" never warns. With neither value known the chip is not shown.

## Settings changed during a turn

While a turn runs the Mode and Model chips and the settings panel stay usable. A pick is validated like any other change, then recorded in the agent host as a **pending change** on the `Connection` (`pendingChanges` in `public()`), so it survives a page refresh and a web-server restart. It does not survive an agent-host restart (the conversation itself needs reconnecting then).

- One pending value per setting; the last choice wins. Choosing the value the agent already has withdraws the pending change. The chip reads "Opus 5.5 → after this turn" with a × that cancels it (`POST /api/live/cancel-pending {id, key}`).
- When the turn ends (result, cancel or error) the host applies the queue in the order chosen through the same validated `session/set_config_option` / `session/set_mode` path, and only then accepts the next prompt (`busy` stays true until the queue is empty).
- If a prompt arrives with changes still pending and no turn running, they are applied first, then the prompt is sent.
- A refused change is dropped, recorded in `changeFailures` (the last 5) and reported once in the page's error banner; the chip goes back to the actual value. A failure never drops or delays the user's prompt beyond the apply attempt.
