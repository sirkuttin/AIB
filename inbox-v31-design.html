Inbox v3.1: stalled, snooze, Windows toast buttons, server-built rows

Design + research, 2026-11-16. Read against main eba14ff, with the code in outputs/agent-studio/. The mockups copy the built inbox (CSS taken from inbox-reply.css, workspace.css .ws-pop / .ws-menu, tokens from theme.css). Every item that goes beyond the owner's words is tagged [Addition].

Owner rules1 Stalled2 Snooze3 Windows toasts4 Server-built rowsPhasesDecisionsSources

In one line each.
  • Stalled: a chat whose agent stopped mid-work without saying it was done goes into Needs you, worded "Stopped mid-work…", with Continue · Reply · Mark handled. Three signals; two of them don't exist yet (each is about 10 lines in connection.ts).
  • Snooze: right-click a Needs-you row (long-press on the phone) and pick Later today (1 hour) or Tomorrow morning. The row leaves and the count drops. It comes back at that time, or sooner if the chat changes. A quiet "1 snoozed" sits in the foot.
  • Windows toast buttons: a small GUI-subsystem helper written in Go, built into the AIB-keeper binary we already ship (AIB-keeper toast). It shows real toasts with Allow / Deny / Continue / a Reply box. It registers AIB's app id and click handler in HKCU (no installer, no shortcut change). If anything fails, AIB falls back to today's tray balloon. About 3 builder-days.
  • Server-built rows: one GET /api/live/inbox serves the PC, the phone, the toasts and the trays. Today four places build their own rows and counts. It goes first because the other three items get cheaper on top of it.
Total ≈ 9 builder-days in 4 phases. Two owner decisions are at the end.

Owner rules this design keeps

How v3.1 keeps them: no new section headers above the list (Snoozed only appears at the bottom, and only when you click), no new colours, no reason words on rows, still one row of actions at most, and no keyboard hints. Snooze adds nothing visible to a row. Toast buttons let you answer without opening AIB, which is "be notified, not wait" taken one step further.

1. Stalled: the agent stopped mid-work and never said it was done

Why. The usage study (usage-data-2026-11-13.md §4 fact 2) found that "OMP stopping silently … happened 3 times, each noticed 5 to 11 hours later". Today such a chat simply leaves the inbox. A connection that closes is phase closed (inbox-rules.js basePhase: if (x.closed) return 'closed'), and the failed-turn rule deliberately skips it. connection.ts:4727 "Failed (the inbox): only the agent's own answer to this prompt, never a Stop or a chat that closed under it."

Where it lives in the rules

  • New phase stalled in inbox-rules.js, added to BLOCKED. That puts it under Needs you, and it counts in the badge, title and tray. A stalled chat is blocked: nothing happens until you act.
  • phaseOf checks the stalledAt mark before the early closed return, and only when stalledAt > handledAt (the same pattern as failed and asks).
  • S1 and S2 are saved as a chat mark (studio-conversations.json, next to handledAt, conversations.ts:21) by the watcher, because a closed connection can drop out of the live list. S3 is live only: it clears itself when output resumes.
  • Sending anything (Continue, Reply, a phone reply) clears it, like failed (connection.ts:4624).

3. Real buttons on Windows' own notifications

Today

AIB's desktop notifications on Windows are a tray balloon: Shell_NotifyIconW(NIM_MODIFY, NIF_INFO) on AIB's tray icon (server/desktop/notify.ts, tray_win.ts). Windows 10/11 draw it as a toast, but a balloon can't carry buttons or a text box, and a click only reports NIN_BALLOONUSERCLICK (bring AIB forward, open the chat). It is always silent (NIIF_NOSOUND). The header of notify.ts says why it was picked: "Nothing is installed, no shortcut AppUserModelID or COM activator is needed, and no process is started." AIB already makes a Start-menu shortcut on first run (shortcut.ts, through WScript.Shell, which can't set the AUMID property). The server already decides when to notify (watcher.ts), so toasts arrive even with the window closed to the tray.

What a button toast needs on Windows

  1. An app identity (AUMID) that Windows maps to a name and an icon. For an app with no installer, Microsoft's unpackaged-app route is a registry key: HKCU\Software\Classes\AppUserModelId\<AUMID> with DisplayName, IconUri and CustomActivator. No Start-menu shortcut property is needed. This is what the Windows Community Toolkit's ToastNotificationManagerCompat and go-toast's SetAppData do. The older route (a shortcut carrying System.AppUserModel.ID + ToastActivatorCLSID) is what Electron + Squirrel installers use.
  2. A way back when a button is pressed. There are two kinds:
    • Protocol activation: the button opens aib://…. It is simple, but it can't deliver what was typed in a text box, and each click starts a new AIB.exe that forwards to the running one.
    • COM activation: a class implementing INotificationActivationCallback, registered under HKCU\Software\Classes\CLSID\{…}\LocalServer32. Windows calls it with the button's arguments and the typed text. If nothing is running, Windows starts the registered exe. This works from the Action Center hours later too.
  3. The toast itself: WinRT ToastNotificationManager.CreateToastNotifier(aumid).Show(...) with ToastGeneric XML. It has to be called from a native thread with COM set up.

Recommendation: B, AIB-keeper toast

  • Why the keeper binary: it already ships for every build, it is GUI-subsystem on Windows ("it can never get a console window"), it is started detached and hidden, and it is Go, the easiest language here for COM. No new binary goes in the zip. It is a separate subcommand, so the keeper's own protocol and constitution stay untouched.
  • While AIB runs: the AIB server starts AIB-keeper toast once, hidden (the same flags as the keeper: DETACHED_PROCESS | CREATE_NO_WINDOW), and talks JSON lines over its stdin/stdout. Show: {op:'show', id, tag, xml}. Remove: {op:'remove', tag}. Clicks come back as {op:'activated', args, inputs}. The helper calls CoRegisterClassObject for AIB's CLSID, so clicks reach the running helper with no new process.
  • AIB closed to the tray: the same as above (the server is still running).
  • AIB fully quit (the agents keep running in the keeper): Windows starts AIB-keeper.exe toast -Embedding from LocalServer32. The helper writes the click to <data>/toast-inbox.json and starts AIB.exe. AIB applies it after start-up, but only if that request is still open; otherwise it just opens the chat.
  • Registry, written at every AIB start (zip builds move around; this is the same idea as ensureStartMenuShortcut, but plain registry writes from Go, so no PowerShell): AppUserModelId\AIB.Studio {DisplayName "AIB", IconUri = a PNG in the data folder, CustomActivator = AIB's fixed CLSID} and CLSID\{…}\LocalServer32 = "<this build>\AIB-keeper.exe" toast. Only HKCU, never admin. The last build started owns the keys, which is fine for one user.
  • Fallback: if the helper fails to start, crashes, or Windows refuses the toast, AIB uses today's balloon for that notification and logs why once. quietReason() (presentation mode, full screen) still applies first.
  • Safety: every button carries a one-time nonce (req=<request key>&n=<nonce>). The AIB server only accepts a nonce it issued, for a request that is still open, so a crafted activation can't approve anything. Answers are logged as "Allowed on Windows notification" (answers.ts, by: 'pc'). Risky commands (push, force push, delete: the row's Review) never get Allow on a toast, only Open.
  • Calm: one toast per chat (tag = chat, group = "aib"), so a newer one replaces the older. When a request is answered anywhere (the row, the phone, the chat), AIB removes that toast from the Action Center (ToastNotificationHistory.Remove) [Addition]. The grouped "3 agents are waiting for you" stays button-less: a click opens the inbox. Default toast scenario only (no "reminder" toasts that stay on screen); Finished stays silent.

Desktop apps ignore activationType="background" (Microsoft's quickstart: "ignored for desktop apps"). Every click reaches the COM activator, and the helper decides not to bring a window up for Allow / Deny / Send / Continue. Only "Open" and a body click bring AIB forward.

What moving them to the server buys:

  • One source of truth. Badge = title = tray = phone envelope = toast text, always (the architect's break 12, test inbox_counts_e2e_test.ts).
  • PC, phone and remote-PC parity for free. Stalled, snoozed and every future row kind are written once. The phone stops guessing.
  • Rows that outlive a connection. A stalled chat whose agent is gone is a row from the marks file; only the server can see that.
  • Less page work. No N+1 detail fetch per row. The server caps the request body (≤ 2 KB per string, a diff head of ≤ 40 lines: architect break 13).
  • Notifications and rows can't disagree. The toast text is the row's line 1.

Owner decisions (2)

1. Where does Snooze live on a row?

a ★ Right-click on the PC / long-press on the phone only. In practice: rows look exactly as they do today, with nothing new to see. You right-click a Needs-you row and pick "Snooze 1 hour" or "Snooze until tomorrow". Cost: you have to know it's there (the row's tooltip says "Right-click to snooze"). Recommended because snooze was "weakly supported" in your own usage (5% of questions sat over 4 h), so it shouldn't cost every row space.

b A quiet "Later" word in the action row of Needs-you rows, next to Mark handled. Click it and the two times appear. In practice: every blocked row gets one more grey word on its single action row. Easier to find, but busier.

2. Can a Windows notification approve a command with one click?

a ★ Yes, for ordinary approvals. In practice: "Run npm install stripe@18.0.0" pops up with Allow / Deny, you click Allow without AIB opening, and the agent carries on. Risky commands (push, force push, delete) still only get "Open", so you see the full command first, as the inbox does today. Risk: an Allow clicked in a hurry from a 2-line toast that shows less than the row does. The command text is still on the toast.

b No. Toasts carry Reply / Retry / Continue, but approvals only get "Open". In practice: every approval still needs AIB in front of you (one more click and a window switch per approval). Safer, but it gives up most of the "be notified, not wait" gain for approvals. You mostly run in bypass mode (0 approvals last week), so either choice matters most when approvals are on.

  • Teams / Slack / VS Code: the new Teams is an MSIX-packaged app and gets toast activation from its package manifest (option C's route); Slack desktop is Electron with a COM activator; VS Code uses Electron's plain notifications without action buttons and keeps answers in its own window. These are the three ends of the same trade-off; AIB's zip and no-installer rule point to B.
